# 문서별 구성 선택

사용자가 준 목차·양식이 우선이다. 아래는 선택 가능한 기본 구성이다. 불필요한 항목은 제거하고 자료에 없는 내용을 채워 넣지 않는다.

## 기술 설계서

목적과 배경 → 범위 → 요구사항 → 설계와 데이터 흐름 → 인터페이스/설정 → 대안과 선택 이유 → 검증 기준 → 미결 사항.

구현된 사실과 사용자·자료가 제시한 설계를 구분한다. 새로운 설계 제안을 요청받은 경우에만 별도 제안으로 작성하고 구현된 것으로 표현하지 않는다. API가 있으면 메서드·경로·요청/응답·오류를 자료에 근거해 정리한다. 저장소 분석 시 핵심 파일과 근거 위치를 연결하되 로컬 경로를 다른 독자도 접근 가능한 링크인 것처럼 표현하지 않는다.

## 운영 절차서

목적과 적용 대상 → 사전 조건 → 실행 단계 → 성공 확인 → 실패 시 대응/복구 → 참고 자료.

각 단계에 작업과 확인 가능한 결과를 붙인다. 명령은 실행 환경과 변수를 명시한다. 자료에 없는 복구 명령은 추측하지 않고 질문한다. 확인 예정 상태로 기재하는 것은 사용자가 그 표현을 확인한 경우에만 허용한다. 문서 작성 과정에서 운영 명령을 실행하지 않는다.

## 회의록

회의 제목과 제공된 일시·참석자 → 안건별 기록 표.

기본 표의 열은 안건 / 논의 요점 / 결정 사항 / 후속 작업 / 미결 사항이다. 여러 주제는 안건별 행으로 구분하며 한 주제로 합치지 않는다. 논의된 의견과 확정된 결정을 구분하고 후속 작업은 작업마다 담당·기한을 함께 적는다. 한 안건에 여러 작업이 있으면 모두 유지한다. 안건의 경계나 결정·작업의 소속이 불분명하면 먼저 확인한다.

자료에 없는 결정·담당·기한은 질문하고 확정 또는 미정 상태를 확인한다. 미결 사항이 없으면 해당 열을 생략할 수 있다. 긴 셀은 목록이나 같은 안건의 세부 행으로 나누고 셀 병합·중첩 표는 피한다. 사용자·회사 양식의 지정 구조가 우선이며 기존 회의록 일부 수정에는 새 형식을 강제하지 않는다.

소수의 주요 안건을 각각 자세히 기록하는 양식은 [주요 안건 회의록](../assets/templates/meeting-focused.md)을 사용한다. 회의 정보 아래에 실제 안건별 제목을 두고, 각 제목 아래에 논의 요점 / 결정 사항 / 후속 작업 / 미결 사항의 세로 표를 반복한다. 안건 수를 맞추려고 내용을 만들거나 서로 다른 안건을 합치지 않는다. 미결 사항은 기재할 내용이 없으면 해당 행을 생략할 수 있다. 기존 한 표 방식과 선택 기준은 [템플릿 적용 규칙](templates.md)을 따른다.

## 장애 보고서

사건 요약 → 영향과 범위 → 타임라인 → 원인 분석 → 조치와 복구 확인 → 재발 방지 → 남은 확인 사항.

확인된 원인과 사용자·자료가 제시한 가설을 구분한다. 원인 분석 항목을 채우려고 새로운 가설을 만들지 않는다. 가설 제안을 요청받았다면 검토 가설로 분리하고 원인으로 확정하지 않는다. 타임라인에는 제공된 시간대와 실제 확인된 시각만 쓴다. 회복 추정과 복구 검증을 구분한다.

## 일반 안내/변경 사항

독자가 알아야 할 변화 → 영향 대상 → 필요한 행동 → 적용 시점 → 참고 자료.

기술 구현보다 독자의 행동을 먼저 설명한다. 한두 문단으로 충분하면 목차나 관리용 메타데이터 표를 만들지 않는다.
